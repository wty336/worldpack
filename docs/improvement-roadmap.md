# 改进路线图：外部对标与演进方向 v0.1

> 本文档整理了 2026-09-07 对引擎的一次全面评审结论：以四类外部项目为参照（见 §1），
> 结合 M1~M2b 三次复盘的遗留项，给出可执行的改进清单（§3~§8）与分批计划（§9）。
>
> 用途：① 作为 M2c/M3 的输入与选型依据；② 每项改进含「现状 → 问题 → 方案 → 验收」，
> 可单独拆出执行；③ 延续项目惯例——每批独立可验收，做完一批验证一批，避免多件事一起上。
>
> 与设计文档的关系：本文档不改写 design.md 的既有决策，只提出演进方向；
> 某批实施完成后，按惯例回写 design.md 与对应复盘（最小 diff + 可回滚）。

## 1. 外部对标结论

| 参照项目 | 它的强项 | 对我们的意义 |
| --- | --- | --- |
| AI Dungeon / NovelAI | 纯自由生成，无结构 | 反面参照：我们的「大纲节点链 + 代码真值」正是它最大的短板，这是差异化优势，**不要丢** |
| SillyTavern | 角色卡 + Lorebook（关键词触发、token 预算、插入深度） | 上下文「按需注入」的成熟范式（§4 B 系列） |
| Friends & Fables | AI GM + D&D 5e 规则：数值驱动玩法（skill check） | 「数值不只记录、要驱动叙事」的样板（§6 D 系列） |
| Stanford Generative Agents | 记忆流 + 检索（recency/importance/relevance）+ 反思 | 记忆系统的下一代形态（§3 A 系列） |

**总体判断**：工程质量（协议闭环、真值校验、压缩曲线、复盘文化）已超过多数同类开源项目；
差距集中在三处——**记忆读取侧（检索/反思缺失）、玩法数值深度（只记录不驱动）、模型分层（设计有、代码未落地）**。

## 3. A 系列 · 记忆系统：从「全量注入」走向「检索 + 反思」

> 差距最大的一项。当前写入侧（remember 提议 → 引擎校验，append-only）是**对的，保留**；
> 要升级的是**读取侧**与**结构化程度**。涉及模块：`memory.py`、`context.py`、`game.py`。

### A1 检索式注入（recency + importance + relevance）

- **现状**：`player_facts` 上限 24 条全量常驻状态栏（memory.py `PLAYER_FACTS_LIMIT`）；
  NPC 记忆按 `memory_limit`（默认 20）全量注入角色卡区块。
- **问题**：条目增长后爆 token、稀释注意力；M2a 迭代 5「事实桶 8→24」已是此矛盾的预演——
  靠调大上限治标，不治本。
- **方案**：注入前对候选记忆打分 `score = α·recency + β·importance + γ·relevance`
  （Generative Agents 三因子），按当前场景/在场 NPC/最近对话取 top-K（K 可配，默认 8~12）。
  relevance 的 v1 实现可用关键词重叠，v2 换 embedding。
- **验收**：事实桶扩到 50+ 条时，状态栏 token 不随条目数线性增长；
  记忆回归集（memory_regression.py）召回@40 保持 100%。
- **✅ 已完成（P1）**：`rank_facts`（score = 0.4·recency + 0.4·importance + 0.2·relevance，
  relevance v1 = 上下文字符二元组重叠，上下文 = 场景+节点目标+近 2 条玩家发言）+
  **常驻区（top importance 3，R1 的常驻强化发现）+ top-K（默认 10）**，玩家事实与
  NPC 记忆均适用。离线：60 条 vs 20 条事实状态栏长度基本恒定（Δ≤200 字符）。
  真机召回见 `docs/p1-report.md`。

### A2 重要性打分（importance）

- **现状**：所有事实权重平等，淘汰纯按回合时间衰减（memory.py `bucket.sort(key=round)`）。
- **问题**：「玩家救过沈清秋的命」与「玩家爱喝龙井」同权，前者可能被挤掉。
- **方案**：remember 工具与提取器输出增加 `importance: 1~10` 字段（提示词给出打分锚点示例）；
  淘汰与检索均以 importance 加权。`MemoryEntry` 增加字段，存档 `to_dict/from_dict` 兼容（缺省 5）。
- **验收**：构造「1 条高重要 + 满桶低重要」场景，高重要事实不被淘汰；
  133 项离线测试全绿（含新增用例）。
- **✅ 已完成（P1）**：`MemoryEntry.importance`（1~10，缺省 5，旧档兼容）；remember 工具
  schema 与提取器输出（`重要性|事实`）均带打分锚点；淘汰按 `(importance, round)` 加权。
  离线：高重要事实在满桶低重要中存活；「旧大事 vs 旧琐事」低重要先淘汰。

### A3 反思层（reflection）

- **现状**：记忆是扁平事实列表，无「从零散观察合成高层洞察」的能力。
- **问题**：20 条「沈清秋对玩家微笑/道谢/赠诗」摆在那里，模型得自己归纳出「她正在动心」——
  归纳负担甩给了生成模型。
- **方案**：每 N 回合（可配，默认 10）或某 NPC 记忆新增满 M 条时，
  用一次轻量调用把近期记忆合成 1~2 句**关系洞察**（「沈清秋对玩家的态度正从客气转向信任」），
  作为独立条目注入角色卡。洞察条目保留来源引用（哪些事实合成而来），支持被新洞察替换。
- **验收**：NPC 语气在长局中的一致性（对照 T4 rubric「人格稳定」）；
  洞察与底层事实矛盾率 = 0（Judge 复核）。
- **✅ 已完成（P1）**：`npc_insights`（带来源事实引用、新替旧、每 NPC 至多 2 条）；
  每 N 回合（CLI 默认 10）对记忆新增达 8 条的 NPC 轻量合成 1~2 句关系洞察，注入角色卡；
  失败静默。离线：触发门控/来源映射/cap 替换/注入/存档回环全绿。
  真机洞察矛盾率（Judge 复核）见 `docs/p1-report.md`。

### A4 语义去重

- **现状**：去重靠字符串包含（`m.fact in fact or fact in m.fact`）。
- **问题**：语义重复挡不住（「剑名听雨」vs「佩剑唤作听雨」），M2a 遗留项。
- **方案**：v1 先用 Judge 同款轻量模型做「是否与既有记忆语义重复」判定（写入时一次调用）；
  v2 再考虑本地 embedding。注意保持写入路径失败静默降级。
- **验收**：语义近义事实注入测试集（10 组）重复拦截率 ≥ 80%。
- **✅ 已完成（P1）**：写入路径字符串去重未命中 → bigram 预筛（无二元组重叠零调用）→
  一次轻量模型判定（temperature 0，失败静默）。真机 10 组近义对拦截 **9/10 = 90%**；
  预筛实测使无重叠事实零模型调用；判定调用成本 ¥0.002。

## 4. B 系列 · 上下文工程

### B1 Lorebook 式世界设定按需注入

- **现状**：`world.yaml` 的 core_rules/style_guide/forbidden 全量进静态前缀；NPC 目录全员常驻。
- **问题**：世界包一大（10 NPC、几十条设定），静态前缀撑爆 KV Cache 预算——
  而「换包即玩任意世界」是 engine 的核心承诺。design.md §4.3 的渐进式披露目前只做到了 NPC 卡。
- **方案**：世界设定拆分为**带触发关键词的 lore 条目**（地点/势力/物品/传闻，
  参照 SillyTavern World Info），按「当前场景 + 最近对话命中关键词 + token 预算」动态注入；
  NPC 目录降级为一行式可发现性索引（现状已接近，保持）。
  schema 变化：`world.yaml` 增加 `lore: [{id, keys, text, budget?}]`。
- **验收**：构造含 30+ lore 条目的测试包，静态前缀 ≤ 8K（design.md §4.6 预算）；
  命中条目的叙事一致性由 Judge 复核。
- **✅ 已完成（P3）**：`world.yaml` 增加 `lore: [{id, keys, text}]`（id 唯一、keys/text
  非空校验）；`context.select_lore` 按「场景+节点目标+近 2 条对话」关键词命中 → 命中数
  降序、字符预算（1500）内追加注入动态区末尾；lore 零入静态前缀。离线：35 条 lore 测试包
  前缀 4.3K（≤8K）且 lore 全隔离；真机：东市 lore 命中注入、西市零注入、Judge 复核通过。

### B2 摘要近期偏置治理（M2b 复盘 #7 遗留）

- **现状**：增量摘要 =「新内容合并旧摘要」，300 轮沙盒中观测到核心关系线被支线稀释。
- **方案**（M2b 复盘 §9 已列候选，此处固化为任务）：
  压缩提示词要求「人物关系单独成节、优先保留」；或摘要与 NPC 记忆定期对账。
- **验收**：在**带轨道**的真实世界包上跑一次 300 轮长局（M2b §9.5 的未决检验），
  三重锚点（mainline + flags + NPC 记忆）下核心关系线存活；感情线 flag 不因摘要漂移丢失。

## 5. C 系列 · 模型分层与成本

### C1 三档模型落地（design.md §14.2 已设计、未实现）

- **现状**：主生成、Judge、压缩、事实提取全部走同一个 `settings.model`。
- **方案**：`config.py` 增加 `judge_model` / `compress_model`（缺省回退主模型）；
  Judge（分类任务）与压缩（摘要任务）换便宜小模型，主生成保持强模型。
  这正是 design.md 的 Sidecar 思路，只是补上实现。
- **验收**：同 seed 300 轮，总成本下降可测（配合 C2 的 usage 记账）；
  Judge 判定质量不回退（用 E1 的对抗用例集复核）。
- **✅ 已完成（P1）——验收口径修正（以实测为准）**：`Settings.judge_model/compress_model`
  + `LLMClient.model_for(purpose)` 路由 + `from_settings` 落地，全部调用点按用途打标。
  实测发现：**当前 DeepSeek 目录仅 flash/pro 两档，主模型默认已是 flash（便宜档），
  不存在更便宜可切换档位**——「总成本下降」的条件是主模型切 pro 后侧信道留 flash
  （侧信道约占 2/3 单价差）。E1 门禁双模型实测：flash Judge 三类 100%/100%/100%、
  pro Judge 100%/83%/83%（pro 默认思考模式吃 500 token 预算致空判定，且贵 5.8×）——
  **质量与成本都指向 flash 才是对的 Judge 模型**，这正是 R3 兜底的价值。

### C2 usage 记账（M2b 复盘 #8 遗留）

- **现状**：长跑脚本只记 token 粗估，API 侧 usage 未落盘（M2b #8：「成本是一等指标」）。
- **方案**：`LLMClient` 统一采集每次响应的 `usage` 字段，追加写入存档旁的 `usage.jsonl`；
  长跑/验收脚本输出累计成本报告。
- **验收**：任意一次长局运行后，可精确回答「这局花了多少钱、输入/输出/缓存各占多少」。
- **✅ 已完成（P1）**：`usage.py`（UsageTracker 逐调用 JSONL 落盘 + 按 (模型, 用途) 汇总 +
  成本报告）；`LLMClient` 全路径采集（含流式 `stream_options.include_usage` 捕获末尾 chunk
  usage），purpose 打标（turn/judge/compress/extract/reflect/dedup）；缓存命中/未命中分别
  记账；价格表为 2026-09 官方峰谷分时快照（可 env 覆盖）。CLI 与全部脚本接入，
  退出时输出成本报告。离线 9 项测试全绿。

## 6. D 系列 · 玩法深度：数值从「记录」到「驱动」

> 当前最像 demo 的部分。切入点是 schedule.yaml：3 行动、固定收益、银两无处可花、
> 武功高低不影响任何判定。参照 Friends & Fables：D&D 5e 让数值通过 skill check 驱动叙事。

### D1 日程行动检定（skill check）

- **方案**：ActionSpec 增加可选 `check: {stat, difficulty}`；
  执行时按 `f(属性, rng)` 分出大成功/成功/失败三档，各档对应不同效果与叙事提示
  （事件系统已有 `chance` 与 rng 注入，机制上是顺的）。引擎把检定结果写入给 LLM 的回合提示。
- **验收**：同行动高/低属性各跑 N 次，成功率差异显著；审计日志零偏差（audit 保留集不退化）。
- **✅ 已完成（P2）**：`ActionSpec.check`（stat/difficulty/margin/noise），
  roll = 属性 + 均匀噪声 → 大成功/成功/失败三档独立效果，检定结果写入 LLM 回合提示
  （`【行动检定】…`）。实测：难度 20 行动下属性 5 vs 45 各 200 次，成功率 0% vs 100%
  （差 100pp）；50 次混合检定后审计零偏差。rng 与事件同源同 seed。

### D2 数值消费闭环

- **方案**：给银两开消费口——如新增行动「备礼探访」（silver -20，affection +4）；
  世界包层落地，引擎无需改动（验证引擎通用性的好案例）。
- **验收**：ancient_jianghu 包内形成「赚钱 → 消费 → 好感 → 事件/结局」的完整数值循环。
- **✅ 已完成（P2）**：新增「备礼探访」（requires 已结识+银两≥20；charm 检定三档好感
  +2/+4/+6，银两恒 -20）+「回礼」日程事件。**实施与原文冲突**：实测「引擎无需改动」
  不可行——无门槛时消费行动会在银两不足时越界/免费刷好感，闭环退化；故做了最小引擎
  扩展 `ActionSpec.requires`（复用条件 DSL，actions_available 过滤 + 执行兜底）。
  60 天闭环模拟：好感达 80、银两恒非负、审计零偏差。

### D3 收益曲线

- **方案**：固定收益改范围随机或边际递减（如修炼收益随武功等级衰减），提升养成策略感。
- **验收**：数值收敛性测试（1000 次模拟无溢出/无负循环）。
- **✅ 已完成（P2）**：效果值支持 `{base, spread?, decay_every?, decay_step?}`
  （范围随机 + 边际递减，最低 0 无负循环）。**设计决策**：世界包效果路径越界统一
  饱和（记录实际生效 delta——先截断 delta 再算 after，审计不变量 `after == before+delta`
  恒成立）；LLM 提议路径保持严格拒绝。修炼 base 4 ±1、每 20 点武功 -1（45 → +2，85 → +0）。
  1000 天模拟无溢出/无负循环/审计零偏差。

## 7. E 系列 · 评估与工具链

### E1 Judge 灵敏度验证（M2b §5.4 观测空白，**最高优先**）

- **背景**：300 轮长局中 Judge 零拦截——无法区分「质量好」还是「判据钝」。
  **一个从未被触发过的校验器等于没有校验器。**
- **方案**：构造 OOC / 设定矛盾 / confabulation 三类**对抗用例集**
  （离线 fake 叙事样本 + 真机小样本），断言 Judge 对每类的拦截率。
- **验收**：三类用例各 ≥ 5 条，拦截率 ≥ 80%；正常叙事误报率 ≤ 10%。
  若判据太钝，先调 JUDGE_SYSTEM 再谈别的。
- **✅ 已完成（P0）**：语料 `game_agent/judge_corpus.py`（OOC 6 / 设定矛盾 6 / confab 6 /
  正常 12），材料与生产同款（status_text，判定依据在材料内可见）；`scripts/judge_sensitivity.py`
  真机门禁（Judge 固定 temperature=0）。实测：ooc 6/6、setting 6/6、confab 5/6（漏判经复测
  为 API 偶发空响应，非判据盲区）、误报 0/12；3 轮多数票复测见 `docs/p0-report.md`。
  **未调 JUDGE_SYSTEM——判据本身够用**。

### E2 结局可达性动态模拟（design.md §13 T2 的完整实现）

- **现状**：worldpack.py 只做了静态校验（completion 的 flag 必须有写入路径）。
- **方案**：引擎离线遍历关键选择全组合（节点数小，组合可控），模拟推进到各结局，
  断言每个 auto 结局的 `when` 可满足。
- **验收**：check-worldpack 输出「结局可达性报告」；不可达结局加载期即拒绝。

### E3 世界包脚手架（M3 目标的前置）

- **方案**：`python -m game_agent init-worldpack <name>` 生成模板目录（六个 YAML 骨架 + 注释手册）；
  配套 check-worldpack 输出「作者友好」的校验报告（现状已较好，再补 schema 示例链接）。
- **验收**：M3 判据——新作者仅凭 design.md §12 + 脚手架，1 周内写出过质量门的包。
- **✅ 已完成（P3）**：`python -m game_agent init-worldpack <name>` 生成六个带注释 YAML
  骨架（B1 lore / P2 检定/门槛/收益曲线活样板 + 示例节点/事件/结局），**生成即过
  check-worldpack**（模板自身过质量门的工程原则）；check-worldpack 报告补规范链接。
  「1 周写出过质量门的包」为 M3 人工判据，工具侧已交付（离线 3 项测试全绿）。

## 8. F 系列 · 工程修复项

### F1 start() 硬编码内容文案（真 bug，违反分层原则）

- **现状**：`game.py` `start()` 写死 `"（游戏开始）你踏入了长安城。"`——
  「长安城」是 ancient_jianghu 的内容，换包即穿帮。**引擎层硬编码了内容层文案。**
- **方案**：开场提示改由 `world.yaml` 的 `opening` / `start_scene` 驱动；
  缺省时用中性文案（「游戏开始」）。

### F3 侧信道异步化

- **现状**：事实提取 / Judge / 压缩都在主循环内阻塞，回合延迟变长。
- **方案**：三者均为失败静默的侧信道，天然适合异步（线程池/任务队列）；
  注意历史写入的顺序一致性（压缩必须与主回合互斥）。
- **验收**：同 seed 下回合延迟（wall clock）下降；压缩与主回合无竞态（结构不变量测试兜底）。

### F4 存档槽位

- **现状**：单槽位（save.json / autosave.json），无存档列表与元信息。
- **方案**：多槽位 + 元信息头（时间戳/天数/当前节点/一句话进度）；
  存档格式带 version 的设计已支持平滑演进。
- **验收**：CLI 支持 `/save <槽位>` `/load <槽位>` `/saves` 列表。

### F5 Web 前端（M2c 可选项）

- **现状**：CLI 已有流式回调 `on_text`，后端基础已铺好。
- **方案**：FastAPI + SSE/WebSocket 包一层会话 API，前端先做一个极简聊天页。
- **验收**：浏览器内完成开局 → 关键抉择 → 存档读档全流程。
- **✅ 已完成（P3）**：`game_agent/web.py`（FastAPI 会话 API + POST-SSE 流式回合
  （delta/done/error 事件，复用 on_text 回调）+ 内嵌极简聊天页）+ `python -m game_agent web`。
  离线 TestClient 全流程 7 项测试全绿；真机 uvicorn：开局 → 抉择（617 个流式增量）→
  发言（247 个增量）→ 行动 → 存读档全流程通过（`scripts/web_smoke.py`）。
