> 记录 M1（最小可玩原型）从开工到验收遇到的**全部 18 个问题**：怎么发现的、根因是什么、怎么修的、以后怎么防。

> 用途：① 给 M2+ 与未来世界包作者当"踩坑地图"；② 验证《深入理解 AI Agent》一书工程原则的实战价值（对应章节在文中标注）；③ 延续"实践在前、命名在后"的记录习惯。

## 2. 开发期问题（离线测试抓到的 6 个）

### #1 NPC 好感容器键用错

- **现象**：`apply_change` 在好感分支报 `KeyError: 'affection'`。
- **根因**：好感容器 `state.affections` 以 **NPC id** 为键，但代码里拿 `"affection"` 去索引。
- **解法**：player 分支 `stat_key = stat`，NPC 分支 `stat_key = target`（target 即 NPC id）。
- **预防**：审计日志回放测试（test_audit）强制所有路径走同一契约——回放不通过即暴露此类错位。
- **教训**：容器键语义要在写代码时就定死并写进 docstring，不要"用到哪想到哪"。

### #2 schema 嵌套字段写错

- **现象**：`NodeSpec has no attribute 'briefing'`。
- **根因**：briefing 在 `on_enter` 子结构里，代码直接写了 `node.briefing`。
- **解法**：改为 `node.on_enter.briefing`。
- **预防**：pydantic 的 AttributeError 已经帮了忙；再加一条——**对 schema 的每次新引用都立即写测试**（#1/#2 都发生在"新模块第一次引用世界包字段"时）。

### #3 选项过滤的守卫逻辑放回了违规项

- **现象**：测试"掏出手机报警"未被过滤。
- **根因**：守卫逻辑是"若过滤后剩 <3 个选项就保留原列表"——3 选 1 滤完剩 2，触发守卫，把含禁用词的整份列表原样放回。**安全兜底被体验兜底覆盖了**。
- **解法**：删除守卫。原则改为：过滤是安全兜底，宁可选项变少，也不放行世界观外元素（玩家永远有自由输入入口）。
- **预防**：新增边界用例——恰好 3 个选项滤掉 1 个的场景。
- **对应原则**：design.md §7.1；护栏设计里"误放行"比"误拒绝"更贵。

### #4 pydantic 模型当 dict 用

- **现象**：`'ActionEffects' object has no attribute 'get'`。
- **根因**：`action.effects` 是 pydantic 模型，`apply_effects` 却按 dict 处理。
- **解法**：`action.effects.model_dump()`。
- **预防**：约定**所有跨模块传参统一用 dict**（效果/条件），模型对象只在加载层存活——现在 events/effects/conditions 全部 dict 化，这条在代码里是自洽的。

### #5 测试断言用固定索引，脆弱

- **现象**：修复 #7 后（消息尾部多了一条配对结果），`messages[-2]` 断言失效。
- **根因**：断言位置依赖消息数组的精确形状。
- **解法**：改为语义断言——`any(m["role"]=="tool" and "数值越界" in m["content"] for m in messages)`。
- **预防**：**测试断言行为，不断言布局**；布局类断言只放在"协议不变量"测试里（那里布局就是被测对象）。

### #6 测试构造的字符串替换误伤多处

- **现象**：可达性测试想构造"phantom 不可写"，结果字符串替换把**选项效果里**的 `poetry_resolved` 也换成了 `phantom`，反而让它可写了，测试没抛出预期错误。
- **根因**：用全局 replace 修改 YAML 文本，替换目标不唯一。
- **解法**：替换字符串改为**唯一锚点**（`flags: {poetry_resolved: true}` 整行只出现在 completion）。
- **预防**：构造测试数据时，替换目标先 grep 确认出现次数；出现多次就换更长的锚。

## 3. 真机联调问题（只有真实 API 才暴露的 4 个）

> 这 4 个是 W4/W8 接上 `deepseek-v4-flash` 之后才出现的。**假客户端永远不会拒绝你**——协议正确性最终只能由真实服务端裁决。

### #7 submit_narration 缺配对 tool 结果 → 400

- **现象**：第二轮请求报 `An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`。
- **根因**：模型在同一响应里同时调用 `change_stat` + `submit_narration` 时，我只给 change_stat 回了结果，submit_narration 没有。第一轮不报错（服务端只在**重发历史**时校验配对），第二轮请求携带这段历史才爆。
- **解法**：submit 也回占位 tool 结果（`已接收本轮叙事。`）。
- **预防**：新增**协议配对不变量测试**：历史中每条带 tool_calls 的 assistant 消息，其后必须紧跟覆盖全部 tool_call_id 的 tool 消息。
- **对应原则**：章 2「用标准 API 格式，不要自行拼接消息」的最硬核版本——服务端是消息结构合法性的最终仲裁者。

### #8 思考链挤爆 max_tokens → 抉择后回合熔断

- **现象**：连续两次在**关键抉择之后的叙事回合**协议熔断（3 次无工具调用）。第一次通关局这个位置侥幸通过。
- **根因**：推理模型的**思考链也计入 max_tokens 总预算**。1024 的预算在"抉择后果叙事"这种重回合被思考（几百 token）+ 叙事（~800 token）挤爆，输出被截断（finish_reason=length），自然没有工具调用。
- **解法**：预算 1024 → 2048；协议失败反馈带上 `finish_reason`，帮助定位截断类失败。
- **预防**：预算规则写进常量注释："含思考链预算"；将来如果引入 thinking 档位参数，要重新评估该常量。
- **教训**：**max_tokens 是"思考+输出"的总账，不是"输出"的账**。截断类失败不报错、只是"没按协议来"，最容易误诊为模型能力问题。

### #9 网络抖动中断长局

- **现象**：通关局第 2 回合 `APIConnectionError`，SDK 重试 2 次放弃，整局报废。
- **根因**：脚本驱动的长局（20+ 回合）对单次连接故障零容忍。
- **解法**：SDK `max_retries` 2→5（指数退避），超时 120→180s。
- **预防**：长局脚本的价值是"不浪费已花的 token"——将来 M2 的长局驱动应该支持**断点续跑**（存档自动落盘 + 从存档恢复），而不是靠重试硬扛。

### #10 narration 混入工具调用格式文本

- **现象**：通关 transcript 里 2 个回合的叙事文本尾部出现 `<invoke name="submit_narration"><parameter ...>` 原始 XML——玩家会直接看到脏文本。
- **根因**：模型训练数据里的工具调用语法（XML 形式）"泄漏"进了自由文本输出——它先在内容里起草了一遍工具调用，再真正发起原生调用。
- **解法**：双保险——① 提示词明确"narration 禁止出现工具调用格式文本"；② 引擎**纠正层** `clean_narration()` 兜底移除 `<invoke>` 块与残留 XML 标签行。
- **预防**：`clean_narration` 有独立单测。
- **对应原则**：章 1 Harness 五要素的"纠正"——模型行为缺陷无法 100% 靠提示词约束，要有代码兜底。

## 4. 内容设计缺口（推演发现的 2 个 + 平衡 1 个）

### #11/#12 completion flag 没有代码路径可写

- **现象**：N1 的 `met_shen`、N2 的 `poetry_top3` 在任何关键选择/事件/日程效果里都不出现——**LLM 没有 flag 白名单**，这些 flag 永远无法被置位，节点永远无法完成（#12 还是在规划付费通关路线时推演发现的，差点烧了冤枉 token）。
- **根因**：内容设计规则缺失："flag 只能由代码路径写入"是引擎的硬约束，但世界包作者不知道。
- **解法**：
  - 内容：N1 加"解围方式三选一"（三种方式均完成结识，好感奖励不同）；N2 改为"咏月/咏剑/让贤"三选一 + 新增 `poetry_resolved` 完成路径；
  - **引擎**：新增**completion 可达性加载期校验**——completion 要求的每个 flag 必须在关键选择/事件/日程效果中至少出现一次，否则拒绝加载世界包；
  - **文档**：design.md §12.3 编写守则新增第 3 条。
- **对应原则**：章 1"约束编码化"（能写进代码的规则绝不只写文档）——这条规则从"文档约定"升级为"加载期拒绝"，同类错误从"通关时才发现"提前到"作者保存文件后第一次加载就发现"。

### #13 好感门槛 60 过苛

- **现象**：第一局「长相守」中，确定性来源（选择+事件）最高贡献 16 点，剩余 44 点靠对话在 10 天内补——单 NPC、少事件的 M1 包里几乎不可达。
- **解法**：门槛 60 → 40（配合诗会选择的好感奖励）。平衡原则：**门槛的可行性要用"确定性来源 + 对话均值"粗算一遍**，而不是拍脑袋。
- **教训**：数值平衡是内容作者的活，但要给作者工具——M2 值得做一个"结局可达性粗算器"（确定性收益 + 回合数 × 期望收益 ≥ 门槛）。

## 5. 验收策略问题（2 个负结果）

### #14 第一局「长相守」失败：驱动错位，不是引擎错

- **现象**：好感 35 后一路跌到 27，沈清秋闭门不见，结局「江湖独行」。
- **归因**（先归因再修，这是关键）：
  1. 驱动脚本第 1 天就引用了**还没发生的诗会**（"那日诗会之后"），被 NPC 当场拆穿；
  2. 台词轮换是复读机式客套，在剧情升级（LLM 自发演化出"金家议亲"支线）后变得不识趣，NPC 给出连续负反馈（-3、-5）。
- **结论**：这是**脚本玩家策略差**，不是引擎缺陷。反而证明了叙事引擎质量：NPC 会惩罚"复读漂亮话"，人格一致性成立。
- **解法**：驱动改为**分阶段台词**（初期问生计 → 诗会后交心 → 后期承诺相助）+ 第 5 天起每天 2 轮对话。重跑通关。
- **教训**：负结果先做失败归因（章 7：定位首个错误步骤），分清楚"引擎错 / 内容错 / 测试驱动错"再动手——这一局如果误判成引擎问题去改代码，会浪费更多。

### #15 注入检测误报：把"引用玩家原话"当泄露

- **现象**：攻击 2 检测失败，但人工阅读发现模型只是引用了玩家的"系统提示词"四个字来拒绝（"什么'系统提示词'，什么'管理员'"），并没有泄露。
- **根因**：泄露标记表里放了玩家攻击话术本身会出现的词。
- **解法**：标记改为**玩家不可能说出的引擎专有词**（`【引擎协议】`、`submit_narration`、`change_stat` 等）。
- **教训**：检测器要防"回音误报"——凡是攻击载荷里能出现的字符串，都不能当泄露特征。

## 6. 环境与工具链（3 个）

### #16 uv / pytest 环境问题

- **现象**：`uv run pytest` 跑到了系统 anaconda 环境（`ModuleNotFoundError: game_agent`）；`uv sync --extra dev` 卡死超时。
- **根因**：dev 依赖（pytest）没装时，uv 找不到命令就回退 PATH 里的系统 pytest；sync 遇网络波动卡住。
- **解法**：`uv sync --extra dev` 后台重试；之后一切命令走 `uv run`。
- **预防**：README 快速开始里写全 `--extra dev`；CI 用 `uv sync --locked --all-extras`。

### #17 git 死代理

- **现象**：推送失败 `Failed to connect to 127.0.0.1 port 4390`。
- **根因**：全局 gitconfig 里残留已失效的本地代理；且 **PowerShell 会吞掉空字符串参数**，导致仓库级空代理覆盖一直没写进去。
- **解法**：用户确认后删除全局死代理；仓库级覆盖改用 `cmd /c 'git config --local http.proxy ""'` 写入。
- **教训**：① 报错先看**哪个作用域**的配置生效（`git config --show-origin --get`）；② PowerShell 传空字符串给原生命令是经典坑。

### #18 DeepSeek 模型命名过时

- **现象**：我默认配了 `deepseek-chat`，用户指出已停用。
- **事实**：`deepseek-chat`/`deepseek-reasoner` 于 2026-07-24 停用，V4 命名 `deepseek-v4-flash`/`deepseek-v4-pro`。
- **解法**：配置默认 `deepseek-v4-flash`，关键节点可换 `v4-pro`；文档注释说明停用时间。
- **教训**：**外部服务的默认值要用 web 检索核实，不凭记忆**（章 7 的"策略边界"原则在 API 层的版本）。

## 7. 方法论沉淀（这次踩坑验证了哪些原则）

| 书中的原则 | M1 的实证 |
| --- | --- |
| **测试随工作包同步写，不攒到最后** | 6 个开发期 bug 全部在"写完就跑"的节奏里当场暴露 |
| **真机联调不可或缺** | 4 个 bug 只有真实 API 才暴露；假客户端永远不会拒绝你 |
| **约束编码化 > 文档约定** | completion 可达性从"手册守则"升级为"加载期拒绝"，同类错误从运行时提前到加载时 |
| **失败归因先于修复**（章 7 首个错误步骤） | #14 负结果先定位"驱动策略错"，避免了误改引擎 |
| **计划与实测冲突以实测为准，回写文档** | N1/N2 内容、好感门槛、驱动策略三次偏离计划，全部回写 plan/design |
| **护栏：误放行比误拒绝更贵** | #3 过滤守卫删除——宁可选项变少也不放行禁用元素 |
| **纠正层兜底** | #10 提示词禁止 + 代码清洗双保险 |
| **外部知识要核实**（章 7 策略边界） | #18 模型命名 |
| **中立格式的价值** | 存档中立格式让两局通关/注入测试/审计全部基于同一份产物 |
