## 4. 六个发现

### ① 【静默丢数据】`card_id` 跨模块重复 → 质检剔除连坐，账目对不上
- **证据**：`_build_module` 对**每个模块**都用 `generate_card(seed_base + i, i, module)`，
  而 `card_id = f"sc-{seed}-{seq:04d}"`（schema 校验也只认 `sc-{seed}-\d{4}`，**不含模块**）
  → 同一层里 extract/judge/compress 的第 i 张卡**共用同一个 id**。
  实测：train 69 条样本只有 **29 个唯一 id**（24 个跨模块重复）；dev 72/30；eval 69/29。
- **已发生的后果（不是推测）**：`main` 里质检剔除写的是
  `samples = [s for s in samples if s["id"] not in bad_set]` —— 按 id 全量过滤，
  一个被点名的 id 会**同时删掉三个模块的副本**，而日志报的是 `len(bad_ids)`：

  | 层 | 90 张卡 − 丢弃 18 = built | 出库 | **实际剔除** | **日志报告** |
  | --- | --- | --- | --- | --- |
  | train | 72 | 69 | **3** | 1 ❌ |
  | dev | 72 | 72 | 0 | 0 ✅ |
  | eval | 72 | 69 | **3** | 1 ❌ |

  两份证据互相印证：被点名的 id（train `sc-10015-0015`、eval `sc-30015-0015`）在三个模块文件里**同时消失**。
- **影响**：① 每层最多 3 条样本被无记录地删掉；② **id 不能当主键**——评委报告、
  人读清单、我的「定 X」对齐（按 id 关联两条轨道）都建立在 id 唯一之上；
  ③ 任何下游用 id 做 join/去重的训练数据管线都会**静默错配**。
- **修法方向**：id 里带模块（`sc-{seed}-{module}-{seq}`）或按模块错开 seed/seq；
  `write_layer` 加"层内 id 唯一"硬校验（不唯一即拒写）；质检剔除日志改成打印**实际删除条数**。
- **为何算最严重**：它不报错、不改数量级，只让数据**少几条且对不上账**——正是"空 = 未知 ≠ 通过"要防的形态。

### ② 轨道 2 探针检出 67% → 批作废（阻断「定 X」）
- **证据**：`reports/rubric-eval-20260912.json`：`probe_detection=0.667`、`batch_valid=false`。
  3 个探针里 **「删要点」漏检**：探针确实删掉了含「沈砚」的两条承诺句（承诺送沈砚去灰雀号），
  评委仍给 **保真 = 2**——它按 anchor（`灰雀号`）字面还在就放行，没判"要点是否还在"。
- **影响**：轨道 2 的成绩不可信 → **定 X 无数据基础**（spec §7.3：批作废则先修评委提示词，不定 X）。
- **口径提示（诚实边界）**：本批只有 **3 个探针**（22 条 × 10%），90% 门等价于"**零漏检**"；
  单次漏检即整批作废。生产规模（300 条 → 30 探针）下这个门才是它设计的样子。
- **修法方向**：评委「保真」判据从"要点词在不在"改成"**该要点是否仍可据摘要复原**"；
  或给探针加"部分覆盖"坏法（删一半）。

### ③ 评委三维饱和（区分度 ≈ 0）
- **证据**：19 条干净样本上 `保真` 18 条满分、`结构` 19 条满分、`流畅` 19 条满分；
  只有 `简洁` 有分布（0/1/2 = 2/16/1）。
- **影响**：四维里三维没有区分度 → 成对比较/选优会退化成随机（spec §12 决策 12 预警的
  "评委只看像不像摘要"在**同一批**上实锤）。
- **根因**：出库样本是**程序先杀的幸存者**（超长/虚构/缺要点已在上游被杀），幸存者本就干净。
- **修法方向**：把区分度检验放到**被杀候选**或非程序筛过的材料上；或给饱和维度定"天花板判据"。

### ④ compress 单模块丢弃率 20~33%，全部因「超长」
- **证据**：三层 `候选全杀` = 10/30、8/30、5/30（eval 另 1 条 `历史演绎丢弃`）；
  出库样本里 10 条被杀候选的失败模式**全部是 `超长`**；
  出库摘要长度 559~799 字（中位 651），而 `SUMMARY_MAX_TARGET = 800` 字。
- **关键点**：丢弃率与卡长**无关**（600 / 3000 / 20000 三类卡都是 ~1/3）——
  模型瞄准 800 字上限写，约 1/3 的卡四个候选全越界。
- **影响**：整批靠 extract/judge 的低丢弃率才把批级丢弃率拉回 20%（门 30%）。
  **若只跑 compress（生产批 300 条就是这种形态）→ 33% > 30% → 批作废。**
- **修法方向**：提示词给上限留余量（目标写 600 字），或把"超长"从刚性杀改成
  "≤800 直接过 / 800~1000 扣分参选"（同步 `compression.py` 的常量口径）。

### ⑤ 「长输入档 20K」名不副实：配额标记取自**卡面**而非**文本**
- **证据**：卡面 `history_spec.target_tokens` 分 600 / 3000 / **20000** 三档；
  实测**最长一次演绎输出仅 4,323 token**；出库 compress 的实际历史长度只有
  **404~4,127 字**（中位 1,321~1,468 字 ≈ 0.9~2.7K token）。
  而 `long_input` 标记 = `card.history_spec.target_tokens >= LONG_INPUT_TOKENS`（**看卡面**）。
- **影响**：① 决策 12/18 要的"20K 长输入档"训练样本**实际不存在**，配额达标是名义达标；
  ② 成本表因此偏低（见 `route-a-cost-20260912.md` §3①）；③ 正是决策 18 那句
  **"任何配额都必须同时声明数据源"**要防的事——本处数据源是卡，不是产物。
- **修法方向**：`verbalize_card` 增加长度校验（或按目标长度分档重演）；
  `long_input` 改判**实际文本长度**；manifest 里"卡面/实际"两个数一起写。

### ⑥ confab 幸存率仅 23%（门禁过度剔除）
- **证据**：judge 卡空间 confab 占 **31/90**（8/11/12），出库只剩 **7/60**（2/3/2）；
  同类对比：ooc 卡 28 → 出库 28（100%）、setting 卡 28 → 25（89%）。
  每层 `confab 撞卡` 丢 6/8/10 张（出厂门禁 `hook_gate`，spec §9.2）。
- **影响**：judge 训练批里 confab 严重欠采样（12% vs 卡面 34%），而 confab 恰是**决策 16 要人读复核**的那一类。
- **修法方向**：卡生成器让 confab 卡避开说话人角色卡（撞卡是多开"设定矛盾"通路的技术问题，
  不是内容问题）——门禁本身是对的，该修的是**卡空间**。

## 5. 「定 X」的处置（决策 13 · M4 最后一项）

- **未定**。`scripts/rubric_x_calibrate.py` 在读报告时**拒绝产出 X**（`batch_valid=false` → 退出 1，
  提示"按 spec：批作废则先修评委提示词，不定 X"）——纪律由代码执行，不靠人记。
- **前置条件**：先按发现②③修评委（「保真」判据从字面在位改成"可复原"，并把区分度检验移到
  非幸存者材料上）→ **整批重评** → 再定 X。
- 因此 spec §12.A 决策 13 行**不写 X 取值**，只挂状态指针。
